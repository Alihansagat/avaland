@lesson Сущности и репозитории
JPA отображает классы на таблицы: класс с `@Entity` — таблица, поле с `@Id` — первичный ключ, `@GeneratedValue` — автоинкремент. Реализация JPA в Spring — Hibernate.
Репозиторий — интерфейс, наследник `JpaRepository<Entity, IdType>`. Реализацию Spring создаёт сам: сразу доступны `save`, `findById`, `findAll`, `deleteById`, `count`, а также постраничный вывод `findAll(PageRequest.of(0, 20))`.
Сущности — изменяемые классы с конструктором без аргументов (JPA требует), а наружу через API отдают отдельные DTO, чтобы не раскрывать структуру базы.
```code
import jakarta.persistence.*;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.*;

@Entity
@Table(name = "books")
public class Book {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false, length = 200)
    private String title;
    private int year;

    protected Book() {}                       // нужен JPA
    public Book(String title, int year) { this.title = title; this.year = year; }
    public Long getId() { return id; }
    public String getTitle() { return title; }
    public int getYear() { return year; }
}

public interface BookRepository extends JpaRepository<Book, Long> {}

// Optional<Book> b = repo.findById(saved.getId());
// Page<Book> page = repo.findAll(PageRequest.of(0, 20, Sort.by("year").descending()));
```

@lesson Запросы: методы-имена и JPQL
Spring Data строит запрос по имени метода: `findByTitleContainingIgnoreCase(String part)`, `findByYearGreaterThanOrderByYearDesc(int year)`, `countByAuthorId(Long id)`, `existsByEmail(String email)`.
Сложные запросы пишут в `@Query` на JPQL (запросы к сущностям, а не к таблицам) или нативным SQL (`nativeQuery = true`). Параметры — именованные `:name`.
Чтобы не тянуть всю сущность, используют проекции: интерфейс или record с нужными полями.
```code
import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;
import java.util.*;

public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByTitleContainingIgnoreCase(String part);
    List<Book> findByYearGreaterThanOrderByYearDesc(int year);
    boolean existsByTitle(String title);

    @Query("select b from Book b where b.year between :from and :to")
    List<Book> published(@Param("from") int from, @Param("to") int to);

    record YearCount(int year, long total) {}
    @Query("select new com.shop.BookRepository$YearCount(b.year, count(b)) from Book b group by b.year")
    List<YearCount> countByYear();
}
```
! Имя метода — это запрос: следите, чтобы поля совпадали с полями сущности
! JPQL работает с классами и полями, а не с таблицами и столбцами
! Проекции — когда нужны 2 поля из 30
? mc Какой запрос построит `findByYearGreaterThan(2020)`?
+ Книги с year > 2020
- Книги с year >= 2020
- Количество книг
- Удаление книг
= GreaterThan — строго больше, GreaterThanEqual — больше или равно.

- JPQL быстрее

- Ничем

@lesson Связи и ленивая загрузка
Связи: `@ManyToOne` (много книг у одного автора), `@OneToMany(mappedBy = "author")` (список книг у автора), `@ManyToMany` через таблицу связи. Внешний ключ задаёт `@JoinColumn`.
По умолчанию коллекции загружаются лениво (`LAZY`): книги автора запрашиваются, только когда к ним обращаются. Если в цикле по 100 авторам трогать их книги — получится 101 запрос (проблема N+1).
Решения: `join fetch` в JPQL, `@EntityGraph(attributePaths = "books")` на методе репозитория или проекция с нужными полями. Включайте логирование SQL в разработке, чтобы видеть реальные запросы.
```code
import jakarta.persistence.*;
import java.util.*;

@Entity
class Author {
    @Id @GeneratedValue Long id;
    String name;
    @OneToMany(mappedBy = "author")
    List<Book> books = new ArrayList<>();
}

@Entity
class Book {
    @Id @GeneratedValue Long id;
    String title;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id")
    Author author;
}

interface AuthorRepository extends org.springframework.data.jpa.repository.JpaRepository<Author, Long> {
    @org.springframework.data.jpa.repository.Query("select distinct a from Author a left join fetch a.books")
    List<Author> findAllWithBooks();                  // один запрос вместо N+1
}

// application.yml для разработки:
// spring.jpa.show-sql: true
```
! Коллекции по умолчанию LAZY — следите за N+1
! `join fetch` или `@EntityGraph` загружают связь сразу
! `mappedBy` — у той стороны, где нет внешнего ключа
? mc Что такое ленивая загрузка (LAZY)?
+ Связанные данные запрашиваются из базы только при первом обращении к ним
- Запросы выполняются медленно специально
- Данные никогда не загружаются
- Загрузка в фоне по таймеру
= Это экономит запросы, но может породить N+1.
? out Что выведет код?
```code
int authors = 50;
int lazyQueries = 1 + authors;
int fetchJoinQueries = 1;
System.out.println(lazyQueries + " " + fetchJoinQueries);
```
> 51 1
= Ленивая загрузка в цикле — 1 + N запросов, join fetch — один.

@lesson Транзакции и миграции Flyway
`@Transactional` на методе сервиса выполняет его в транзакции: при исключении изменения откатываются. Внутри транзакции изменённые сущности сохраняются автоматически при коммите — явный `save` не обязателен.
`@Transactional(readOnly = true)` для чтения — небольшая оптимизация. Транзакция работает только при вызове метода снаружи бина: вызов `this.method()` внутри класса её не создаст.
Схему базы не генерируют автоматически в проде (`ddl-auto: validate`), а меняют миграциями Flyway: файлы `V1__init.sql`, `V2__add_index.sql` применяются по порядку при запуске.
```code
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
class TransferService {
    private final AccountRepository accounts;
    TransferService(AccountRepository accounts) { this.accounts = accounts; }

    @Transactional
    public void transfer(long fromId, long toId, long amount) {
        Account from = accounts.findById(fromId).orElseThrow();
        Account to = accounts.findById(toId).orElseThrow();
        if (from.getBalance() < amount) throw new IllegalStateException("Недостаточно средств");
        from.setBalance(from.getBalance() - amount);
        to.setBalance(to.getBalance() + amount);
        // save не нужен: изменения сохранятся при коммите транзакции
    }
}

// src/main/resources/db/migration/V1__init.sql
// create table account (id bigserial primary key, balance bigint not null check (balance >= 0));
// application.yml: spring.jpa.hibernate.ddl-auto: validate
```
! `@Transactional` — на публичных методах сервиса
! В проде `ddl-auto: validate`, схема меняется только миграциями
! Ограничения в базе (`check`, `not null`, `unique`) страхуют от ошибок кода
? mc Что произойдёт с изменениями, если внутри @Transactional-метода брошено RuntimeException?
+ Транзакция откатится, изменения не сохранятся
- Сохранится половина
- Приложение упадёт
- Изменения сохранятся
= Непроверяемые исключения по умолчанию вызывают откат.
? mc Почему в продакшене не используют `ddl-auto: update`?
+ Hibernate может непредсказуемо изменить схему; изменения должны идти через проверенные миграции
- Он медленный
- Он не работает с PostgreSQL
- Это платная функция
= Миграции версионируются и проверяются на ревью.
