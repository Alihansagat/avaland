@lesson Retrofit: запросы к API
Retrofit превращает интерфейс Kotlin в HTTP-клиент: методы с аннотациями `@GET("users/{id}")`, `@POST`, параметры — `@Path`, `@Query`, `@Body`. Функции делают `suspend`, и их вызывают из корутин.
JSON превращается в data-классы через kotlinx.serialization (или Moshi, Gson): поля с `@Serializable`, имена — `@SerialName`, если в API они в snake_case.
Сеть ненадёжна: оборачивайте вызовы в `try/catch` или `runCatching`, обрабатывайте коды ответа и таймауты. Разрешение на интернет — в `AndroidManifest.xml`.
```code
import kotlinx.serialization.*
import retrofit2.http.*

@Serializable
data class RepoDto(
    val id: Long,
    val name: String,
    @SerialName("stargazers_count") val stars: Int,
)

interface GitHubApi {
    @GET("users/{user}/repos")
    suspend fun repos(@Path("user") user: String, @Query("per_page") perPage: Int = 30): List<RepoDto>
}

// создание клиента:
// val api = Retrofit.Builder()
//     .baseUrl("https://api.github.com/")
//     .addConverterFactory(Json { ignoreUnknownKeys = true }.asConverterFactory("application/json".toMediaType()))
//     .build()
//     .create(GitHubApi::class.java)

suspend fun topRepos(api: GitHubApi, user: String): Result<List<String>> = runCatching {
    api.repos(user).sortedByDescending { it.stars }.take(3).map { it.name }
}
```
! Сетевые функции Retrofit — `suspend`, вызывайте их из корутин
! `ignoreUnknownKeys = true` — API добавит поле, а приложение не упадёт
! Каждый сетевой вызов может упасть — обрабатывайте ошибки

@lesson Room: локальная база
Room — обёртка над SQLite: `@Entity` описывает таблицу, `@Dao` — интерфейс с запросами (`@Query`, `@Insert`, `@Update`, `@Delete`), `@Database` связывает всё вместе. SQL в `@Query` проверяется при компиляции.
Метод DAO, возвращающий `Flow<List<T>>`, сам присылает новый список при каждом изменении таблицы — экран обновляется автоматически.
При изменении схемы повышают версию базы и пишут миграцию; иначе после обновления приложения пользователь получит падение или потеряет данные.
```code
import androidx.room.*
import kotlinx.coroutines.flow.Flow

@Entity(tableName = "notes")
data class NoteEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val text: String,
    val createdAt: Long = System.currentTimeMillis(),
    val pinned: Boolean = false,
)

@Dao
interface NoteDao {
    @Query("SELECT * FROM notes ORDER BY pinned DESC, createdAt DESC")
    fun observeAll(): Flow<List<NoteEntity>>

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun upsert(note: NoteEntity): Long

    @Query("DELETE FROM notes WHERE id = :id")
    suspend fun delete(id: Long)
}

@Database(entities = [NoteEntity::class], version = 1)
abstract class AppDb : RoomDatabase() {
    abstract fun notes(): NoteDao
}
```
! Запросы, которые меняют данные, — `suspend`; наблюдение — через `Flow`
! Room не даёт выполнять запросы в главном потоке
! Новая версия схемы — новая миграция

- Одну запись
- Ничего, это ошибка

? mc Что нужно сделать при добавлении нового столбца в Entity в уже вышедшем приложении?
+ Повысить версию базы и добавить миграцию
- Ничего, Room сам всё сделает без потерь
- Удалить приложение у пользователей

= Миграция переносит данные пользователей в новую схему.

@lesson Корутины и Flow
Корутины — лёгкие потоки Kotlin: `suspend`-функции ждут сеть или базу, не блокируя главный поток. В ViewModel их запускают в `viewModelScope.launch { }` — корутины отменятся, когда экран закроют.
Диспетчеры: `Dispatchers.Main` — интерфейс, `Dispatchers.IO` — сеть и файлы, `Dispatchers.Default` — тяжёлые вычисления. Retrofit и Room сами переключаются на нужный поток.
`Flow` — асинхронный поток значений. Операторы `map`, `filter`, `combine`, `debounce` преобразуют его, `stateIn` превращает в `StateFlow` для экрана. Параллельные запросы — `coroutineScope { async { } ... await() }`.
```code
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    val queries = flowOf("k", "ko", "kot", "kotl", "kotlin")
    queries
        .filter { it.length >= 3 }
        .map { "поиск: $it" }
        .collect { println(it) }

    val time = measureTimeMillis {
        val (a, b) = coroutineScope {
            val x = async { delay(300); 1 }
            val y = async { delay(300); 2 }
            x.await() to y.await()
        }
        println(a + b)
    }
    println(time < 550)          // запросы шли параллельно
}

inline fun measureTimeMillis(block: () -> Unit): Long {
    val start = System.currentTimeMillis(); block(); return System.currentTimeMillis() - start
}
```
! Запускайте корутины в `viewModelScope` или `lifecycleScope`, а не в `GlobalScope`
! `async` + `await` — для параллельных независимых запросов
! `StateFlow` — состояние экрана, которое Compose собирает через `collectAsStateWithLifecycle`
? mc Почему не стоит запускать корутины в GlobalScope?
+ Они не отменятся при закрытии экрана и могут работать впустую или течь
- GlobalScope медленнее
- Это не компилируется
- GlobalScope блокирует главный поток
= Структурированная конкурентность привязывает корутины к жизненному циклу.
? mc Что выдаст `flowOf(1, 2, 3, 4).map { it * it }.filter { it > 4 }.toList()`?
+ [9, 16]
- [1, 4, 9, 16]
- [4, 9, 16]
- [3, 4]
= Квадраты 1, 4, 9, 16; больше 4 — 9 и 16.

@lesson Репозиторий и офлайн-режим
Репозиторий объединяет источники данных: экран подписан на базу Room (единственный источник правды), а обновление идёт из сети и записывается в базу. Так приложение мгновенно показывает сохранённые данные и работает без интернета.
Ошибку сети не показывают пустым экраном: данные из базы остаются, а сверху — сообщение «нет связи, показаны сохранённые».
Фоновую синхронизацию по расписанию или при появлении сети делает WorkManager — он выполнит задачу даже после перезапуска телефона.
```code
import kotlinx.coroutines.flow.Flow

class NotesRepository(
    private val dao: NoteDao,
    private val api: NotesApi,
) {
    val notes: Flow<List<NoteEntity>> = dao.observeAll()     // экран читает только базу

    suspend fun refresh(): Result<Int> = runCatching {
        val remote = api.notes()                              // может бросить исключение
        remote.forEach { dao.upsert(NoteEntity(id = it.id, text = it.text)) }
        remote.size
    }
}

// ViewModel:
// init { viewModelScope.launch { repo.refresh().onFailure { _error.value = "Нет связи — показаны сохранённые заметки" } } }
// val state = repo.notes.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
```
! База — единственный источник правды для экрана
! Ошибка сети не должна стирать уже показанные данные
! WorkManager — для синхронизации, которая обязана выполниться
? mc Почему экран читает данные из Room, а не напрямую из сети?
+ Данные показываются мгновенно и без интернета, а сеть только обновляет базу
- Room быстрее Retrofit
- Сеть нельзя вызывать из ViewModel
- Так меньше кода
= Подход offline-first.
? out Что выведет код?


= При ошибке сети показываем кэш и сообщение.
