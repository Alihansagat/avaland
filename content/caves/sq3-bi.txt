@lesson Продуктовые метрики
Базовые метрики продукта: DAU/WAU/MAU (уникальные активные за день, неделю, месяц), липкость DAU/MAU, конверсия, удержание, отток (churn), ARPU (выручка на пользователя), LTV (выручка за всё время жизни клиента), CAC (стоимость привлечения).
Хорошая метрика связана с ценностью для пользователя. North Star — главная метрика продукта (для AVALAND — например, число уроков, пройденных за неделю). Рядом держат защитные метрики, которые не должны ухудшиться (ошибки, отписки).
Метрику оформляют карточкой: определение, формула в SQL, источник данных, владелец, частота обновления.
```code
-- DAU и MAU по таблице events(user_id, created_at)
WITH daily AS (
  SELECT date(created_at) AS day, COUNT(DISTINCT user_id) AS dau
  FROM events
  GROUP BY 1
)
SELECT ROUND(AVG(dau)) AS avg_dau,
       (SELECT COUNT(DISTINCT user_id) FROM events
        WHERE created_at >= date('now', '-30 days')) AS mau
FROM daily
WHERE day >= date('now', '-30 days');

-- ARPU за месяц = выручка / активные пользователи
-- LTV ≈ ARPU в месяц × средний срок жизни клиента в месяцах
-- Юнит-экономика сходится, если LTV > CAC
```
! Каждая метрика — с точным определением и SQL
! Главная метрика + защитные метрики
! LTV > CAC — бизнес зарабатывает на клиентах

- Аудитория 50 человек
= Метрика липкости продукта.

+ Когда LTV клиента больше стоимости его привлечения CAC
- Когда DAU больше MAU
- Когда реклама бесплатная
- Когда retention 100%
= Иначе каждый новый клиент приносит убыток.

@lesson A/B-тесты
A/B-тест сравнивает версии продукта на случайных группах пользователей: A — контроль, B — изменение. Случайное распределение делает группы похожими во всём, кроме изменения.
Перед тестом фиксируют гипотезу, главную метрику, минимальный эффект и нужный размер выборки, срок (целыми неделями). Подглядывать и останавливать тест при первой «значимости» нельзя — растёт число ложных открытий.
Для конверсий считают разницу долей и p-value (z-тест или χ²). p < 0.05 означает: такой разницы при отсутствии эффекта ждать маловероятно. Проверяют и SRM — равны ли размеры групп задуманным.
```code
-- итоги теста по таблице assignments(user_id, variant) и orders
SELECT a.variant,
       COUNT(DISTINCT a.user_id)                                         AS users,
       COUNT(DISTINCT o.customer_id)                                     AS buyers,
       ROUND(100.0 * COUNT(DISTINCT o.customer_id) / COUNT(DISTINCT a.user_id), 2) AS conversion_pct
FROM assignments a
LEFT JOIN orders o ON o.customer_id = a.user_id AND o.status = 'paid'
GROUP BY a.variant;

-- z-тест для двух долей (считают в Python или калькуляторе):
-- p = (x1 + x2) / (n1 + n2)
-- z = (p1 - p2) / sqrt(p * (1 - p) * (1/n1 + 1/n2))
-- |z| > 1.96  → различие значимо на уровне 5%
```
! Гипотеза, метрика и размер выборки — до запуска
! Не останавливайте тест, как только увидели значимость
! Проверяйте баланс групп (SRM)
? mc Зачем распределять пользователей по группам случайно?
+ Чтобы группы различались только изменением, а не составом аудитории
- Так быстрее
- Чтобы было честно перед пользователями
- Это не обязательно
= Иначе эффект смешается с различием аудиторий.
? out Что вернёт запрос?
```code
WITH t(variant, users, buyers) AS (VALUES ('A', 1000, 50), ('B', 1000, 65))
SELECT variant, 100.0 * buyers / users FROM t ORDER BY variant;
```
> A 5.0 B 6.5
> A | 5.0 B | 6.5
> A, 5.0, B, 6.5
= Конверсия контрольной и тестовой группы.
? fill Впишите название проверки: размеры групп отличаются от задуманных 50/50.
```code
Проверка ___ (sample ratio mismatch)
```
> SRM
> srm
= Сломанное распределение обесценивает тест.
? mc Тест показал p = 0.3. Что это значит?
+ Данных недостаточно, чтобы утверждать, что разница не случайна
- Версия B точно хуже
- Версия B лучше на 30%
- Тест нужно повторить вчера
= Отсутствие значимости — не доказательство отсутствия эффекта.

@lesson Дашборды и BI
BI-инструменты (Metabase, Superset, DataLens, Power BI, Tableau, Looker Studio) подключаются к базе и строят графики по SQL-запросам. Дашборд — набор графиков вокруг одного вопроса или одной аудитории.
Хороший дашборд: сверху 3–5 главных чисел с изменением к прошлому периоду, ниже — динамика и разрезы, фильтры по периоду и сегменту. Один график — одна мысль; заголовок формулирует вывод («Выручка выросла на 12% из-за часов»).
Тип графика по задаче: линия — динамика, столбцы — сравнение категорий, гистограмма — распределение, таблица — точные значения. Круговые диаграммы — только для 2–3 долей.
```code
-- запрос для карточки «Выручка за 30 дней и изменение»
WITH r AS (
  SELECT SUM(CASE WHEN o.order_date >= date('now', '-30 days') THEN p.price * oi.qty END) AS cur,
         SUM(CASE WHEN o.order_date <  date('now', '-30 days')
                   AND o.order_date >= date('now', '-60 days') THEN p.price * oi.qty END) AS prev
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  JOIN products p     ON p.id = oi.product_id
  WHERE o.status = 'paid'
)
SELECT cur, prev, ROUND(100.0 * (cur - prev) / NULLIF(prev, 0), 1) AS change_pct
FROM r;
```
! Сверху — главные числа с динамикой
! Заголовок графика — вывод, а не название столбца
! Линия для времени, столбцы для категорий
? mc Какой график подходит для выручки по месяцам?
+ Линейный
- Круговой
- Облако слов
- Карта
= Линия показывает динамику.
? out Что вернёт запрос?
```code
SELECT ROUND(100.0 * (112 - 100) / NULLIF(100, 0), 1), ROUND(100.0 * (5 - 0) / NULLIF(0, 0), 1);
```
> 12.0 NULL
> 12.0 null
> 12 NULL
= Изменение к нулевому периоду не определено — NULL вместо ошибки.


@lesson Отчёт и собеседование аналитика
Результат работы аналитика — решение. Отчёт строится так: вопрос → короткий ответ → доказательства (графики, цифры) → ограничения данных → рекомендация и следующий шаг.
Портфолио: 2–3 проекта на открытых данных — исследование с SQL и визуализацией, дашборд, разбор A/B-теста. Код — на GitHub, дашборд — по ссылке.
На собеседовании дают SQL-задачи (JOIN, GROUP BY, оконные функции, когорты), продуктовый кейс («упала конверсия — как искать причину?») и вопросы по статистике. Рассуждайте вслух: уточните метрику, разложите её на составляющие, проверьте данные и сегменты.
```code
-- кейс: «выручка упала на 15%». Раскладываем: выручка = покупатели × заказы на покупателя × средний чек
WITH m AS (
  SELECT strftime('%Y-%m', o.order_date)  AS month,
         COUNT(DISTINCT o.customer_id)    AS buyers,
         COUNT(DISTINCT o.id)             AS orders,
         SUM(p.price * oi.qty)            AS revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  JOIN products p     ON p.id = oi.product_id
  WHERE o.status = 'paid'
  GROUP BY 1
)
SELECT month, buyers,
       ROUND(1.0 * orders / buyers, 2)  AS orders_per_buyer,
       ROUND(1.0 * revenue / orders)    AS avg_check,
       revenue
FROM m
ORDER BY month;
-- дальше — разрезы: город, категория, источник трафика, новые и старые клиенты
```
! Ответ первым, детали — потом
! Падение метрики раскладывают на множители и сегменты
! Портфолио — проекты с понятным вопросом и выводом
? mc С чего начать, если выручка упала на 15%?
+ Проверить данные и разложить выручку на покупателей, частоту и средний чек, затем смотреть сегменты
- Сразу предложить скидки
- Перезапустить сервер
- Ждать следующего месяца
= Декомпозиция метрики сужает поиск причины.
? out Что вернёт запрос?
```code
WITH m(buyers, orders, revenue) AS (VALUES (100, 120, 600000))
SELECT 1.0 * orders / buyers, revenue / orders, buyers * (1.0 * orders / buyers) * (revenue / orders) FROM m;
```
> 1.2 5000 600000.0
> 1.2, 5000, 600000.0
> 1.2 5000 600000
= Выручка = покупатели × заказы на покупателя × средний чек.

```code

```
> avg_check
> средний
= Средний чек.

+ Короткий ответ на вопрос и рекомендация
